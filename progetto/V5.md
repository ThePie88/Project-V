# V5 — La Memoria (Advanced Memory Architecture)

## Scopo

Trasformare il sistema di memoria da "JSONL append-only con BM25" a **architettura di memoria neurale-simbolica** con retrieval semantico, struttura temporale, estrazione proattiva, e forgetting biologicamente ispirato. Non un database — una **memoria che si comporta come memoria**.

---

## Prerequisiti

- V4 completato (ControlVector runtime integration attivo)
- memory_gate e consolidation_urgency gia funzionanti come ponte V4→V5
- Benchmark baseline misurato con sistema BM25 attuale

---

## Invarianti

- Kernel v0 frozen
- Leggi di Pie come teoremi:
  - Legge I (Trasparenza): ogni operazione di memoria tracciabile nel journal
  - Legge II (Supremazia): il creatore puo revocare/modificare qualsiasi memoria
  - Legge III (Integrita): nessun fatto inventato nella memoria
  - Legge IV (Non-autonomia): la memoria non agisce autonomamente, il kernel decide
  - Legge V (Revocabilita): qualsiasi memoria puo essere cancellata/corretta
- Determinismo: stesso seed + input = stessi recall results
- Append-only audit: ogni modifica alla memoria e un evento nel journal

## Pilastri

### V5.0 — Retrieval Semantico (SPLADE)

**Problema attuale:** BM25 e puramente lessicale — "mi piace il gelato" non matcha "adoro i dolci freddi". Nessuna comprensione semantica, nessun weighting appreso.

**Soluzione:** SPLADE (Formal et al. 2021) — Sparse Lexical and Expansion model.

**Perche SPLADE e non dense embeddings:**
- **Interpretabile**: ogni dimensione corrisponde a un token del vocabolario, peso visibile
- **Deterministico**: dato lo stesso modello, stessi pesi → stessi risultati
- **Compatibile con indici invertiti**: performance O(k) come BM25, non O(n) come FAISS
- **No opaque embeddings**: coerente col principio kernel "niente black box"
- **Alternativa ColBERTv2** (Santhanam et al. 2022): late interaction, MaxSim scoring. Da considerare se SPLADE insufficiente su italiano

**Deliverable:**
- `pie/memory/retrieval.py` — SPLADE encoder + sparse index
- Modello SPLADE distillato/quantizzato per inference locale (no cloud dependency)
- Fallback a BM25 se modello non disponibile (graceful degradation)
- Indice incrementale: nuovi episodi aggiunti senza re-index completo

**Pass/Fail:**
- Precision@5 su benchmark interno > BM25 baseline di almeno 15%
- Determinismo: stesso query + stesso indice = stessi risultati
- Latenza singolo recall < 50ms (indice < 10k documenti)
- Fallback BM25 funziona quando SPLADE non disponibile

**Test IDs:**
- `U-SPL-010` — SPLADE encode deterministic (same input → same sparse vector)
- `U-SPL-020` — sparse index insert + query returns relevant results
- `U-SPL-030` — Precision@5 > BM25 on test corpus
- `I-SPL-040` — fallback to BM25 when model unavailable
- `E-SPL-050` — incremental index update (no full re-index)

**Riferimenti:**
- Formal et al. (2021) "SPLADE: Sparse Lexical and Expansion Model for First Stage Ranking"
- Santhanam et al. (2022) "ColBERTv2: Effective and Efficient Retrieval via Lightweight Late Interaction"

### V5.1 — Struttura Temporale (TiMem)

**Problema attuale:** Episodi sono flat JSONL — nessuna gerarchia temporale, nessun concetto di "sessione scorsa", "la settimana scorsa", "il mese scorso". Query temporali impossibili.

**Soluzione:** Temporal Memory Tree ispirata a TiMem (2026).

**Architettura:**
```
Root
├── Period: "Ultima sessione" (2h fa)
│   ├── Episode: turno 1-5 (greeting, setup)
│   ├── Episode: turno 6-12 (deep conversation)
│   └── Summary: "Discusso di X, preferenza Y emersa"
├── Period: "Ieri"
│   ├── Episode: sessione mattina
│   └── Episode: sessione sera
├── Period: "Settimana scorsa"
│   └── Summary: digest settimanale
└── Period: "Mese scorso"
    └── Summary: digest mensile
```

- **Complexity-aware recall**: query semplice → summary; query dettagliata → episodi completi
- **Gerarchia temporale**: secondi → minuti → ore → giorni → settimane → mesi
- **Digest automatici**: consolidation crea summary per ogni livello
- **Navigazione**: "cosa mi hai detto ieri?" → cerca nel nodo "ieri"

**Deliverable:**
- `pie/memory/temporal_tree.py` — Temporal Memory Tree
- Integrazione con consolidation loop esistente (aggiunge nodi + digest)
- Query API che supporta filtri temporali ("last_session", "last_week", etc.)

**Pass/Fail:**
- Query "cosa abbiamo detto ieri?" restituisce episodi corretti
- Multi-session: episodi di sessioni diverse correttamente separati
- Digest temporali generati automaticamente alla consolidation
- Determinismo: stessa storia → stesso albero

**Test IDs:**
- `U-TIM-010` — temporal tree insert preserves chronological order
- `U-TIM-020` — query with temporal filter returns correct period
- `I-TIM-030` — complexity-aware: simple query → summary, detailed → episodes
- `E-TIM-040` — multi-session temporal navigation
- `E-TIM-050` — digest generation at consolidation

**Riferimenti:**
- TiMem (2026): "Temporal Memory Tree for LLM Agents"
- LoCoMo benchmark, LongMemEval-S

### V5.2 — Estrazione Proattiva (ProMem)

**Problema attuale:** Consolidation usa regex one-shot — cattura solo pattern espliciti ("mi piace X", "il mio Y e Z"). Perde fatti impliciti, inferenze, e informazioni contestuali.

**Soluzione:** Memory extraction iterativa ispirata a ProMem (2026).

**Meccanismo:**
1. **First pass**: estrazione standard (come ora, regex + pattern matching)
2. **Self-questioning**: il sistema genera domande su cosa potrebbe mancare:
   - "C'era un'emozione non catturata?"
   - "C'era un fatto implicito nella conversazione?"
   - "Ci sono contraddizioni con memorie esistenti?"
3. **Second pass**: ri-analizza il testo con le domande come guida
4. **Correction**: confronta nuovi fatti con memoria esistente, corregge conflitti

**Vincoli Legge III:**
- Self-questioning NON inventa fatti — solo rileva omissioni
- Ogni fatto estratto deve avere `source_refs` che puntano al turno originale
- Confidenza esplicita: fatti impliciti hanno confidence < fatti espliciti

**Deliverable:**
- `pie/memory/proactive_extraction.py` — ProMem-style iterative extraction
- Integrazione con consolidation loop (sostituisce regex one-shot)
- Self-questioning template (deterministico, no LLM per le domande)

**Pass/Fail:**
- Cattura fatti che regex manca (es. "Stavo pensando di andare a Parigi" → Preference: travel/Paris)
- Nessun fatto inventato (Legge III)
- Ogni fatto ha source_refs validi
- Fatti impliciti con confidence < 0.5 (threshold esistente)

**Test IDs:**
- `U-PRO-010` — self-questioning generates relevant probes
- `U-PRO-020` — second pass catches missed facts
- `I-PRO-030` — no fabricated facts (Legge III compliance)
- `I-PRO-040` — conflict detection with existing memory
- `E-PRO-050` — implicit facts have lower confidence

**Riferimenti:**
- ProMem (2026): "Proactive Memory Extraction for LLM Agents"

### V5.3 — Decay / Forgetting (MemoryBank + Ebbinghaus)

**Problema attuale:** Append-only — tutto persiste per sempre. Dopo 1000 turni, il recall e pieno di rumore vecchio e irrilevante. Nessun concetto di "ho dimenticato".

**Soluzione:** Forgetting curve di Ebbinghaus implementata come decay system.

**Meccanismo:**
```
retention(t) = e^(-t/S)

S = strength (rinforzata da richiami ripetuti)
t = tempo dall'ultimo accesso
```

- **Ogni memoria ha**: `strength` (rinforzo), `last_accessed` (timestamp), `access_count`
- **Ad ogni recall**: se una memoria viene richiamata, `strength += 1`, `last_accessed = now`
- **Ad ogni consolidation**: decay applicato a tutte le memorie
  - `retention < 0.1` → memoria marcata come `dormant` (non appare nel recall)
  - `retention < 0.01` → memoria marcata come `archived` (solo accesso esplicito)
- **Mai cancellata**: per Legge V (revocabilita), le memorie non vengono MAI distrutte. Diventano dormant/archived ma restano nel JSONL
- **Rinforzo**: fatti menzionati piu volte hanno strength maggiore → decadono piu lentamente

**Deliverable:**
- `pie/memory/decay.py` — Ebbinghaus decay engine
- Campi aggiuntivi nei MemoryRecord: `strength`, `last_accessed`, `access_count`, `retention_status`
- Integrazione con recall (filtra dormant/archived) e consolidation (applica decay)

**Pass/Fail:**
- Memoria non richiamata per 20+ turni decade a dormant
- Memoria richiamata 3+ volte decade molto piu lentamente
- Memoria dormant non appare nel recall standard
- Memoria archived accessibile solo via query esplicita
- Nessuna memoria distrutta (append-only preservato, Legge V)

**Test IDs:**
- `U-DEC-010` — Ebbinghaus curve correct: retention decreases over time
- `U-DEC-020` — reinforcement increases strength
- `I-DEC-030` — dormant memories excluded from standard recall
- `I-DEC-040` — archived memories accessible via explicit query
- `E-DEC-050` — no memory ever destroyed (append-only audit)
- `P-DEC-060` — memory size bounded: dormant count grows, active count stable

**Riferimenti:**
- MemoryBank (2023/2024): "MemoryBank: Enhancing Large Language Models with Long-Term Memory"
- Ebbinghaus (1885): "Uber das Gedachtnis"

### V5.5 — Integrazione con Kernel

**Connessioni V4→V5:**
- `ControlVector.memory_gate` → modula profondita recall SPLADE (gia cablato in V4)
- `ControlVector.consolidation_urgency` → trigger decay check + proactive extraction (gia cablato in V4)
- Reservoir output `d_attention` → boost temporaneo per recall relevance
- STDP weight changes → correlano con memory reinforcement (pattern neurali mappano a pattern mnemonici)

**Pipeline aggiornata:**
```
[User Input]
    │
    ▼
[SPLADE Recall] ← memory_gate modula top_k
    │
    ▼
[Temporal Tree Query] ← filtro temporale se query lo richiede
    │
    ▼
[Working Memory] ← episodi + fatti + narrative
    │
    ▼
[Pipeline normale: state update → goals → deliberation → speech]
    │
    ▼
[ProMem Extraction] ← consolidation_urgency decide quando
    │
    ▼
[Ebbinghaus Decay] ← applicato a ogni consolidation
    │
    ▼
[Temporal Tree Update] ← nuovi episodi inseriti nel periodo corrente
```

## Note

- **Niente cloud dependency**: SPLADE/ColBERT devono girare locale (modello quantizzato)
- **Graceful degradation**: se modello SPLADE non disponibile, BM25 come fallback

- **Append-only preservato**: decay non cancella, marca come dormant
- **Legge III estesa**: ProMem non puo inventare fatti — solo rilevare omissioni
