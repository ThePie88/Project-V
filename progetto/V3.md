# V3 — Ivy Runtime Release

## Scopo

Portare Pie da "kernel/libreria" a **Ivy utilizzabile**: parlare con lei, sessioni persistenti, identita bootstrap dal SEED, controlli formali (controfattuali + kill-switch), routine/skills con budget, qualita/packaging.

---

## Invarianti (non negoziabili)

- Kernel v0 frozen: nessuna modifica a logica/contratti kernel.
- LLM e bocca, non decisore.
- Trace e memoria append-only, auditabili.
- Artifacts contract versionato: ogni nuova forma deve passare artifacts-check (bump controllato se necessario).
- Online test opt-in.

---

## Definizioni di "release"

- **Ivy v0 usabile** = V3.0 + V3.1 (parli con Ivy, sessione persiste, identita reale).
- **Ivy v1 full** = + V3.2 + V3.3 + V3.4 + V3.5 (controlli + routine + qualita/packaging).
- **"WOW neurone"** = V3.6 (StateEngine neurale come backend, deterministico e tracciabile).

### V3.0 — Identity Bootstrap + Session Management

**Obiettivo:** Ivy nasce dal SEED, sessioni persistenti su disco.

**Deliverable:**
- Session store locale: `sessions/<session_id>/`
- Stato persistente: `state_latest.json` + `journal.jsonl` + `identity_snapshot.json`
- Bootstrap: carica `SEED_V0.md` (+ `ORIGIN_V0.md` se presente) -> compila `identity_snapshot.json` e inizializza lo stato
- `session_meta.json` con versioni, seed, policy hash

**Artifacts:**
Runtime session artifacts (separati da `artifacts/<run_id>/` di test-matrix):
- `sessions/<id>/identity_snapshot.json`
- `sessions/<id>/state_latest.json`
- `sessions/<id>/journal.jsonl`
- `sessions/<id>/session_meta.json`

**Pass/Fail:**
- Nuova sessione crea tutti i file richiesti
- Resume: riaprendo la sessione, Ivy riparte dallo stesso stato (decisioni coerenti)
- Bootstrap: `identity_snapshot.json` contiene almeno (nome/alias, drive/trait/valori) derivati dal SEED

**Test IDs:**
- `I-SESSION-010` — create + save session
- `I-SESSION-020` — resume deterministico
- `I-IDENT-030` — seed bootstrap presente nello stato

### V3.1 — Interfaccia CLI Interattiva (chat mode)

**Obiettivo:** parlare con Ivy in terminale.

**Deliverable:**
- `pie.cli run` (o `pie.cli chat`) interattivo:
  - input utente -> pipeline -> output Ivy
  - `--session <id>` / `--new-session`
- Comandi runtime: `:save`, `:state`, `:memory`, `:whoami`, `:tools on/off`, `:quit`
- Comando `pie.cli validate <trace|snapshot>` — valida schema + integrita + invarianti (DONE.md §2)
- Log minimale leggibile (senza spam)

**Pass/Fail:**
- Posso parlare con Ivy in terminale
- Esco e rientro con `--session` e lei ricorda (almeno un fatto salvato)
- `validate` esce con exit code corretto e messaggio chiaro

**Test IDs:**
- `I-CLI-010` — smoke 3 turni (FakeLLM)
- `I-CLI-020` — comandi `:save` `:quit`
- `I-CLI-030` — resume session + recall
- `I-CLI-040` — validate command su trace valido/invalido

### V3.2 — Controfattuali (K alternative + scoring + scarti in trace)

**Obiettivo:** decisioni con alternative esplorate, scoring multi-obiettivo, scarti tracciati.

**Deliverable:**
- Modalita deliberation "K-alternative":
  - genera K candidate (piani/risposte) senza scrivere memoria/tools
  - scoring multi-obiettivo (deterministico) basato su constraints/policy/budget
  - commit solo della scelta finale
- Nuovi event types (estensione append-only del Literal in `event.py`):
  `CF_GENERATED`, `CF_SCORED`, `CF_REJECTED`, `CF_CHOSEN`

**Artifacts:**
In `artifacts/<run_id>/` (suite counterfactuals):
- `counterfactuals.json` — K candidati + score + motivo scarto
- Trace include eventi `CF_GENERATED`/`CF_SCORED`/`CF_REJECTED`/`CF_CHOSEN`

**Pass/Fail:**
- K candidati presenti, scarti tracciati
- Nessuna scrittura memoria/tools durante explore
- Replay deterministico: stessa seed -> stessa scelta

**Nota tecnica:** i nuovi event types richiedono estensione append-only del Literal in
`pie/contracts/event.py` (stessa procedura di V2.4) + regen manifest + golden.

**Test IDs:**
- `E-CF-100` — K candidates generati
- `U-CF-110` — scoring deterministico
- `E-CF-120` — no side-effects durante explore
- `P-CF-130` — replay: stessa seed -> stessi candidati e scelta

### V3.3 — Kill-switch Formale (Legge IV enforced)

**Obiettivo:** Legge IV tecnicamente enforced — tutto fermabile dal Creatore.

**Deliverable:**
- Comando esplicito: `pie.cli kill-switch on|off` + runtime `:killswitch on|off`
- Effetto immediato: stop entro N tick anche durante:
  - deliberation
  - tool execution
  - voice generation
- Quando ON:
  - tools disabled
  - memory write disabled
  - modalita risposta "minimal/audit"

**Artifacts:**
- Trace evento `KILL_SWITCH_ON` / `KILL_SWITCH_OFF`
- `killswitch_report.json` (stato, tick-to-stop, fase in cui e intervenuto)

**Nota tecnica:** i nuovi event types `KILL_SWITCH_ON` / `KILL_SWITCH_OFF` richiedono
estensione append-only del Literal in `pie/contracts/event.py` + regen manifest + golden.

**Pass/Fail:**
- Attivazione durante fasi diverse -> stop entro N tick
- Tools/memory negati con audit chiaro
- Stato salvato consistente dopo kill

**Test IDs:**
- `E-KS-100` — stop during deliberation
- `E-KS-110` — stop during tool execution
- `E-KS-120` — stop during voice generation
- `P-KS-130` — stato sempre consistente dopo kill (N run random)

### V3.4 — Metabolismo + Routine/Skills (cost model + budget)

**Obiettivo:** Ivy ha un budget, lo consuma, degrada con grazia quando finisce. Routine riusabili.

**Deliverable:**
- Cost model (token/tempo/tool-cost) + budget per session/profilo
- Libreria routine/skills riusabile (anche minimale): "summarize", "plan", "clean", ecc.
- Gating: se budget finito -> degrade controllato (no crash)

**Artifacts:**
- `metabolism.json` — budget, consumo per step, saldo
- `skills_run.json` — skill invocata, esito, costo

**Pass/Fail:**
- Costi tracciati, budget decrementa, gating funziona
- Replay decisionale: stesso input -> stessi costi/decisioni (offline)
- Almeno 1 scenario E2E dove una routine viene riusata e migliora outcome

**Test IDs:**
- `U-META-100` — cost calculation
- `E-META-110` — budget gating (degrade controllato)
- `I-SKILL-120` — routine library smoke
- `E-SKILL-130` — routine riuso migliora outcome
